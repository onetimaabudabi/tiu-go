# Математическая модель технической части TIU GO

Модель камеры внутри кабины лифта и алгоритма, который по её показаниям
решает: останавливаться на промежуточном этаже или проехать мимо,
потому что кабина полная.

Здесь только техника. Приложение, прогноз ожидания для пользователя и
выбор «лифт или лестница» — это социальная часть проекта, она живёт
в [`math-model/`](../math-model/) и сюда не заглядывает.

---

## Что моделируется

В корпусе 7 ТИУ шесть лифтов, работают три (№ 1, 2, 6). В каждом
работающем стоит камера с детектором YOLOv8n. Она считает людей
в кабине, а система по этому счёту решает судьбу каждого вызова
с промежуточного этажа.

Остановка стоит дорого: полный цикл дверей — 7 секунд, это как проехать
почти два этажа. Остановка у полной кабины не привозит никого, но
отнимает время у всех, кто уже едет. Задача системы — такие остановки
отсекать, не отсекая при этом те, где человек ещё мог бы войти.

## Что делает каждая модель

| Скрипт | Одной строкой |
|---|---|
| `01-camera-model.js` | Считает, какую часть кабины видит камера и как падает уверенность детекции с ростом числа людей. |
| `02-detection-errors.js` | Разделяет ошибки на систематические (перекрытия) и случайные (мерцание) и показывает, что секундное окно лечит только вторые. |
| `03-decision-logic.js` | Проверяет правило «проехать или остановиться», сравнивает три способа пройти пограничную зону и определяет нужную точность детектора. |
| `04-elevator-physics.js` | Считает время рейса по кинематике кабина-двери-посадка и пропускную способность с системой и без неё. |
| `05-effectiveness.js` | Оценивает решения как классификацию: accuracy, precision, recall, F1 в четырёх условиях работы. |
| `06-simulation.js` | Прогоняет 500 учебных дней с реальным расписанием пиков, сравнивая оба режима на одних и тех же пассажирах. |
| `07-optimization.js` | Перебирает запас мест от 0 до 4 и находит оптимальное значение. |
| `08-report.js` | Собирает всё в Word: 11 разделов, 17 рисунков, 17 таблиц. |
| `09-excel.js` | Собирает книгу из семи листов, где расчётные ячейки — живые формулы Excel. |

## Запуск

Всё сразу:

```bash
npm run tech:all
```

Занимает около полутора минут: симуляция и оптимизация считают сотни
учебных дней. Результаты лягут в `tech-model/output/`.

По отдельности:

```bash
npm run tech:camera     # модель 1
npm run tech:errors     # модель 2
npm run tech:decision   # модель 3
npm run tech:physics    # модель 4
npm run tech:effect     # модель 5
npm run tech:sim        # модель 6
npm run tech:optimize   # модель 7
npm run tech:excel      # книга Excel
npm run tech:report     # Word-отчёт
```

Каждый скрипт работает самостоятельно. Отчёт и Excel берут готовые
результаты из `output/data/*.json`, а если какого-то файла нет —
запускают нужную модель сами.

## Четыре вывода, которые стоит знать

**Геометрию ограничивает не матрица, а плоскость голов.** До пола
от камеры 2.4 м, а до голов — всего 0.7 м, и тот же угол обзора
покрывает там заметно меньшую площадь. При наклоне 47° камера видит
97.6 % плоскости голов и 87.6 % пола; слепая зона приходится на углы
кабины прямо под камерой.

**Способ чтения счёта важнее самого детектора.** Наивное усреднение
числа рамок по 30 кадрам даёт при полной кабине смещение −3.5 человека,
трекинг с подтверждением тремя кадрами подряд — только −1.4. Разница
больше, чем между YOLOv8n и любой моделью потяжелее.

**Монетка в пограничной зоне дребезг не гасит, а создаёт.** В исходной
постановке задачи предлагалось в зоне шириной два места бросать монетку.
Каждое попадание в зону — это новый бросок, и решение переворачивается
в 25 % секунд. Настоящий гистерезис сохраняет предыдущее решение
и снижает дребезг до 2 % — более чем на порядок.

**Запас мест и камеру настраивают вместе.** Запас компенсирует
систематический недосчёт конкретного детектора. Поставить камеру лучше,
не перенастроив запас, — значит начать проезжать мимо свободных мест:
точность решений при зафиксированном запасе с ростом mAP₅₀ не растёт,
а падает.

## Расхождения с исходной постановкой

Модель в трёх местах отходит от формулировок технического задания.
Каждое отступление помечено в коде и объяснено в отчёте.

**Штраф за перекрытия отсчитывается от второго человека.** В постановке
стояло `0.15·(1 − exp(−n/3))`, что отнимает 0.043 уже при одном человеке
в кабине — хотя перекрывать его там некому. Используется
`0.15·(1 − exp(−(n−1)/3))`. Вернуть исходную формулу можно флагом
`camera.useCorrectedOcclusion` в `params.js`.

**Вместо монетки в пограничной зоне — гистерезис.** Обоснование выше;
оба правила реализованы и сравниваются в модели 3.

**Запас мест перебирается до 4, а не до 3.** Чтобы показать, что
оптимум лежит внутри диапазона, а не упирается в его край.

Отдельно стоит отметить параметр `people.avgAreaM2 = 0.08 м²`. Как
оценка вместимости он даёт 12.5 чел/м² — вдвое выше физического предела
давки. Модель использует его там, где он осмыслен (площадь силуэта
в кадре), а вместимость берёт из наблюдений: 10 человек в пик.

## Параметры

Все исходные числа — в [`params.js`](params.js). Менять стоит именно там:
остальные файлы к ним только обращаются.

Этот набор параметров **самостоятельный**: он намеренно не связан
ни с `shared/data/mockData.js`, ни с `math-model/params.js`. Модель
описывает корпус 7 таким, каким он наблюдается сейчас — с тремя
работающими лифтами из шести, — а приложение показывает все шесть.

Те же числа продублированы на листе «Параметры» в `TECH_MODEL.xlsx`,
и там их можно покрутить без кода: расчётные ячейки пересчитаются сами.
